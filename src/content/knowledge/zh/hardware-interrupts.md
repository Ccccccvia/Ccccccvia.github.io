## 设备不必等程序主动询问

假设 CPU 正在执行线程 A，而定时器到期，或网卡完成了一批接收工作。
设备可通过中断机制通知 CPU，不要求 A 正在执行与该设备有关的指令。
这就是“相对于当前指令流异步”：事件来自外部，不是当前指令本身执行出错。

中断减少了持续轮询的需要，但系统也可能混合轮询、中断合并等策略。
一次通知不保证只对应一个数据包，也不意味着所有设备工作已经由 CPU 做完。

## 往返要保留什么

被打断的程序仍需要自己的指令位置、寄存器值和必要的处理器状态。
不是 CPU 自动保存所有内容，也不是处理程序从零猜测这些内容。

| 阶段 | 主要工作 | 关键边界 |
| --- | --- | --- |
| 请求与接收 | 中断控制器和 CPU 按规则递送、接收事件 | 屏蔽或优先级可能延迟接收 |
| 入口与保存 | CPU 保存架构规定的状态，入口软件补存所需寄存器 | 具体集合依架构和入口而变 |
| 向量分发 | 依据向量机制进入相应处理入口 | 向量号不等于处理程序地址 |
| 简短处理 | ISR 确认来源、记录必要状态，按设备协议应答 | 不在高优先级入口做无界工作 |
| 后续工作 | 把较长处理交给适合的延后执行机制 | 执行上下文仍决定能否阻塞 |
| 退出与恢复 | 恢复现场，或先安排其他可运行线程 | 原线程不一定立即继续 |

表中入口保存与分发是概念分工，不是跨所有架构通用的严格微步骤顺序。
在 x86 中，中断向量通常索引 IDT 描述符，描述符再确定入口及相关属性。
入口软件运行前，硬件已经完成选择入口所需的动作。

## ISR 为什么要简短

中断服务程序（ISR）通常只完成紧急、有限的工作，再安排后续处理。
例如先记录设备完成状态并排队，而不是在 ISR 内解析全部收到的数据。

Windows 驱动可把适当工作交给 DPC；Linux 可使用线程化中断或工作队列等机制。
这些机制不是同一种上下文：例如 Windows 普通 DPC 仍不能任意阻塞等待。
需要等待或执行较长任务时，应选择允许这种行为的上下文，而不是只把函数改名。

```text
设备通知 → CPU / 入口保存 → ISR → 排队后续工作
                                   ↓
                            退出路径检查调度
                              ↙          ↘
                         恢复 A       先运行 B
```

后续工作可能与其他任务交错；“排队”不等于“已经处理完毕”。

## 一次定时器通知的示意时间线

假设定时器目标时刻为 `4.0 ms`，当时 A 正在运行。
下面是人为选取的说明性读数，不是某平台的性能测量或时延承诺。

| 时刻 | 示例事件 |
| --- | --- |
| `4.0 ms` | 定时器到期，请求中断 |
| `4.2 ms` | CPU 接收中断，进入处理路径并保存必要现场 |
| `4.3 ms` | 简短处理结束，调度路径选择就绪的线程 B |
| `4.5 ms` | 稍后恢复 A 的现场，让 A 继续 |

请求到入口的示意延迟是 `4.2 − 4.0 = 0.2 ms`。
A 从入口到恢复的示意间隔是 `4.5 − 4.2 = 0.3 ms`，不全是 ISR 执行时间。
中断屏蔽、较高优先级工作和调度都会影响延迟；定时器中断不自动提供硬实时保证。
也不是每次定时器中断都必须切换线程。

## 不要把三种入口混为一谈

| 机制 | 与当前指令的关系 | 示例 |
| --- | --- | --- |
| 硬件中断 | 异步到达 | 定时器到期、设备完成通知 |
| 同步异常 | 当前指令执行触发 | 缺页、除零 |
| 系统调用 | 程序有意请求内核服务 | 通过专用系统调用指令进入内核 |

系统调用可用专用指令，也可在某些系统上使用软件中断指令，不能一概称为硬件中断。
同步异常也不应全部统称为“软件中断”。

不同 CPU 和 OS 的优先级、嵌套和抢占规则不同；不存在通用的设备优先级排行榜。
保存现场让执行有机会恢复，不保证被打断线程何时再次获得 CPU。
