## 先把名字和文件分开

在 Linux 文件系统里，目录项把名字关联到 inode；inode 表示该文件系统内的文件身份及元数据。两个硬链接是同一 inode 的两个名字，不是两份互相独立的文件内容。

其中没有享有特权的「原件」。通过任一名字修改现有文件，改变的都是共享内容。不过，把某个目录项替换为另一文件，是不同的操作。

## 一个指向身份，一个指向路径

假设 `a` 和 `b` 都对应 inode 42。名为 `s` 的符号链接拥有自己的 inode 77，其中保存目标路径 `a`。

```text
a ───────────────► inode 42 ──► data
b ───────────────► inode 42
s ──► inode 77 ──► path "a" ──► inode 42
```

这里的编号仅作示意，不是全局唯一编号。沿着 `s` 访问时，还要解析其中保存的路径；软链接本身不会给 inode 42 增加一个硬链接计数。

## 去掉一个名字会发生什么

假设三个名字都在同一目录中，现在只移除 `a`：

| 观察项 | 移除前 | 移除后 |
| --- | --- | --- |
| inode 42 的硬链接数 | 2 | 1 |
| 通过 `b` 访问 | 可用 | 仍可用 |
| 通过 `s` 访问 | 到达 `a` | 目标悬空 |
| 软链接 inode 77 | 存在 | 仍存在 |

软链接这个对象还在，只是沿目标路径访问会失败。若以后另一文件使用了名字 `a`，没有改动的软链接又可能指向那个新文件。

## 路径与文件系统的边界

- 硬链接必须位于同一文件系统内，普通用户不能为目录创建硬链接。
- 软链接可以指向目录，也可以跨文件系统，但仍受正常访问权限约束。
- 软链接中的相对目标，要从软链接所在目录解析，不是从调用者的工作目录解析。

例如，`shelf/shortcut` 保存 `../items/a`，就会从 `shelf` 的父目录继续定位 `items/a`。

因此，把软链接移到其他目录，即使目标文本没变，实际指向也可能改变。

## 什么时候才能回收空间

最后一个硬链接名字被移除后，链接计数降为零。对于普通文件，还需要没有打开的引用，存储空间才可回收；打开的文件描述符能让一个已经无名的文件继续可用。

```text
links > 0                   → 文件仍有名字
links = 0, open reference    → 文件仍被保留
links = 0, no open reference → 空间可回收
```

这里讨论的是文件生命周期，不是安全擦除。移除链接并不承诺旧存储字节已经被覆盖。

参考：[Linux unlink(2) 手册](https://man7.org/linux/man-pages/man2/unlink.2.html)。
