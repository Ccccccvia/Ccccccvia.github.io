## 有序不等于有消息边界

假设应用在同一条 TCP 连接上先写入 ASCII 字节 `AB`，再写入 `CDE`。五个字节全部传送后，接收方看到的顺序是 `ABCDE`，但 TCP 不会为接收应用保留两次写入的边界。

发送调用成功，只能说明相应字节被本地接受，不代表远端应用已经处理完毕。一次发送也可能只接受部分数据，发送方必须按返回的字节数继续处理。

## 同一条流可以分成不同读取

下表每一行都是这五个字节的一种可能分组。竖线分隔的是读取结果，不是流中新增的字节。

| 读取结果 | 发生了什么 |
| --- | --- |
| `AB │ CDE` | 边界碰巧一致 |
| `A │ BCD │ E` | 写入被拆分，也被合并 |
| `ABCDE` | 两次写入一起读出 |

请求读取 1,024 字节，实际可能返回更少。短读取不表示消息结束，看起来整齐的分组也不是应用边界的依据。

配图采用第二行的分组：字母顺序不变，外围分组却改变了。

## 给正文加上长度前缀

约定使用两字节无符号大端整数，记录正文的字节长度。两条 ASCII 消息就编码为：

```text
[00 02] A B [00 03] C D E
   2 bytes      3 bytes
```

`00 02` 和 `00 03` 表示十六进制头部字节，不是要发送的可见文本。长度只计算正文，不包括头部自身的两个字节。

整条示例流共有九字节：四字节头部加五字节正文。这是应用协议制定的规则，不是 TCP 自动添加的格式。

## 先累积，再取出完整帧

把新收到的字节追加到缓冲区，然后重复执行：

1. 不足两字节，等待头部补齐。
2. 解出长度 `L`，先检查它是否超过约定上限。
3. 不足 `2 + L` 字节，等待正文补齐。
4. 交付正文，恰好消费 `2 + L` 字节，继续检查剩余数据。

| 新收到的字节 | 处理结果 | 缓冲区剩余 |
| --- | --- | --- |
| `00` | 头部不完整 | `00` |
| `02 A B 00` | 交付 `AB` | `00` |
| `03 C` | 正文不完整 | `00 03 C` |
| `D E` | 交付 `CDE` | 空 |

交付 `AB` 后若直接清空整个缓冲区，就会丢掉下一帧头部的第一个字节。

## 还要约定哪些边界

长度计算编码后的**字节数**，不是 Unicode 字符数；一个字符可能占多个字节。两端必须约定编码、头部字节序和正文长度上限。

两字节头部最多表示 65,535 字节正文，应用可以设置更小上限。连接关闭时若仍有不完整帧，应视为输入被截断，而不是一条完整消息。
