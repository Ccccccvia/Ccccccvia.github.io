## 两个数字描述不同的事

动态数组模型用一段连续的元素槽位保存序列，并分别记录有效长度和存储容量。
这里画的是语言中立的模型，不是某个语言数组对象的内存截图。

| 记录 | 回答的问题 | 初始示例 |
| --- | --- | --- |
| `size` | 现在有几个有效元素？ | 3 |
| `capacity` | 不扩容时最多可容纳几个元素？ | 4 |
| `capacity - size` | 还能追加几个而不扩容？ | 1 |

正常状态满足 `0 ≤ size ≤ capacity`。
元素的有效下标范围是 `0 ≤ index < size`，不是 `index < capacity`。

## 从三个元素开始

下面 `--` 表示空余容量，不是元素值，也不是一个可读取的占位元素。

```text
index:          0    1    2    3
size=3, cap=4: [10] [20] [30] [--]
size=4, cap=4: [10] [20] [30] [40]

index:          0    1    2    3    4    5    6    7
size=5, cap=8: [10] [20] [30] [40] [50] [--] [--] [--]
```

最初下标 3 虽然位于缓冲区容量内，却不属于这个序列的有效元素。
追加 40 是由容器执行的操作：写入新元素后，把 `size` 从 3 更新为 4。
这不意味着调用者可以绕过接口，直接把所有预留槽位当成已有元素。

## 第四个便宜，第五个可能搬家

| 时刻 | size / capacity | 需要做什么 |
| --- | --- | --- |
| 初始 | 3 / 4 | 保存 10、20、30，剩一个空位 |
| 追加 40 后 | 4 / 4 | 使用剩余槽位，不必扩容 |
| 准备追加 50 | 4 / 4 | 已满，先取得更多容量 |
| 追加 50 后 | 5 / 8 | 保留原四个元素，再加入 50，剩三个空位 |

本例选择把容量从 4 扩到 8，并假设分配了一个新缓冲区。
先把四个有效元素依次迁移过去，再放入 50，更新容器记录并释放旧存储。

**翻倍只是示例策略**，不是所有语言或库的共同要求。
某些底层存储可以原地扩展；需要新缓冲区时，原有元素的次序仍应保持。
连续槽位也不等于元素引用指向的对象都相邻，更不意味着深拷贝那些对象。

## 为什么单次 O(n)，摊还却是 O(1)

设当前有 n 个元素，且每个槽位的读取、写入或迁移都是常数成本。
若元素自身的复制很昂贵，还需要计入那个成本。

| 操作 | 模型中的成本 | 原因 |
| --- | --- | --- |
| 按下标读取 | O(1) | 可根据起点与固定槽位大小定位 |
| 有空位时尾部追加 | O(1) | 写入一个新槽位并增加长度 |
| 需要复制到新缓冲区的追加 | O(n) | 迁移 n 个已有元素，再追加 |
| 几何扩容下的连续尾部追加 | 每次摊还 O(1) | 总迁移量与追加次数同阶 |
| 中间插入 | 最坏 O(n) | 即使容量足够，也要移动后面的元素 |

从固定的小容量出发，若每次翻倍，扩容迁移量形成 `4 + 8 + 16 + …`。
连续追加 m 次时，这个几何级数的总量为 O(m)，再加上 m 次新元素写入仍为 O(m)。
因此每次追加的摊还成本为 O(1)，但触发扩容的那一次依然可能是 O(n)。
摊还分析是在计算整段操作的总成本，不是在承诺每一次的延迟，也不是随机输入的平均情况。
若每次只增加一个槽位，反复复制可能累计到 O(m²)，就没有上述结论。

## 有空位也不能免费插到中间

在 `[10, 20, 30]` 的下标 1 插入 15，需要先为它腾位置。
即使已有空余容量，也要先把 30 向右移，再把 20 向右移，最后写入 15。
得到 `[10, 15, 20, 30]` 后，长度增加；保持次序才是这些移动的原因。
尾部追加不需要移动后缀，所以不能把它的摊还成本套到中间插入上。

## 概念相似，API 不统一

一些容器公开容量：例如 .NET `List<T>` 区分 `Count` 和 `Capacity`，C++ vector 区分 `size()` 和 `capacity()`。
预留更多容量本身不增加有效元素；删除一个元素也不一定立即缩小容量。
空容器可以是 `size = 0` 且容量仍大于 0，这并不矛盾。

JavaScript `Array` 没有这里这种标准容量 API，语言也不保证它连续存储。
尤其不能把稀疏数组的 `length` 直接当成这个模型中有效元素的数量。
