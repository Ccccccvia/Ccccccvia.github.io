## 一套地址空间，多条执行路径

同一进程中的线程通常共享虚拟地址空间，包括代码、全局数据和堆。
两个线程拿到同一个有效堆对象的地址后，可以访问同一个对象，而不必复制一份。
这同时带来协作能力和冲突：操作系统调度线程，不会替应用自动维护对象的不变量。

| 状态或区域 | 线程之间的关系 | 要注意的边界 |
| --- | --- | --- |
| 地址空间、代码、全局数据、堆 | 同进程线程共享 | 访问仍受权限、对象生命周期和语言规则限制 |
| 寄存器上下文、指令位置 | 每个线程分别保留 | 切换执行时要保存与恢复必要状态 |
| 逻辑调用栈 | 每个线程有自己的栈与调用过程 | 栈内存通常仍位于共享地址空间 |
| 线程局部存储 TLS | 每个线程有自己的实例 | “线程局部”不等于硬件隔离的秘密区域 |

“有自己的栈”描述执行组织和生命周期，不是其他线程绝对无法访问的内存墙。
如果把有效栈对象的地址交给另一个线程，它可能访问该对象；仍须保证生命周期和同步。
原线程返回后继续使用已经失效的局部对象，不会因它曾来自栈就变安全。

## 并发不一定是并行

并发表示多个任务在同一段时间内推进，可能是在一个逻辑 CPU 上轮流执行。
并行表示某一时刻确实有多个任务同时执行，需要硬件与调度条件支持。

| 场景 | 并发 | 必然并行吗？ |
| --- | --- | --- |
| 一个逻辑 CPU 交替运行 A、B | 是 | 否 |
| 两个可用逻辑 CPU 同时运行 A、B | 是 | 此时并行 |
| 创建两个线程，但其中一个在等待 | 可以构成并发任务 | 不保证 |

即使没有同时执行，读改写中间发生切换也足以产生逻辑竞争。

## 两次加一，为什么只留下一个一

设共享 `counter` 初始为 `0`，A 和 B 各想把它增加 `1`。
把操作概念上拆成“读取、在自己的临时值上加一、写回”。

| 步骤 | 线程 A | 线程 B | 共享 counter |
| --- | --- | --- | --- |
| 0 | 尚未操作 | 尚未操作 | 0 |
| 1 | 读取 0 到自己的临时值 | — | 0 |
| 2 | — | 读取 0 到自己的临时值 | 0 |
| 3 | 临时值从 0 算成 1 | — | 0 |
| 4 | — | 临时值从 0 算成 1 | 0 |
| 5 | 写回 1 | — | 1 |
| 6 | — | 写回 1 | 1 |

两次意图上的增加应该合计为 `2`，但这个概念交错只留下 `1`：一次更新丢失。
表格是教学用的抽象步骤，不是可执行程序，也不承诺具体机器指令如何拆分。

尤其不能据此声称：无同步的 C++ 普通整数数据竞争，运行结果只可能是 `1` 或 `2`。
C++ 中这种 data race 属于未定义行为，不能把此表当作实际输出保证。

## 锁要保护整个读改写

让所有参与访问的线程遵守同一个同步协议，把“读取—修改—写回”放在同一临界区。
只在读时加锁一次、写时再加锁一次，仍会留下两者之间的竞争窗口。

```text
A：取得锁 → 读 0 → 加一 → 写 1 → 释放锁
B：取得同一把锁 → 读 1 → 加一 → 写 2 → 释放锁
```

这是一种合法顺序；B 也可以先取得锁，但受保护的两次增加不会互相覆盖。
只给一个线程加锁，而另一个线程绕过协议访问同一数据，不能得到这种保证。

## 原子加法解决的是哪一层问题

对单个计数值，可以使用有明确定义的原子加法，把增量作为不可分割的读改写操作。
若两次增加都遵守同一原子访问方案、没有其他重置，并按同步规则观察完成后的值，结果是 `2`。
普通“加一”的写法或某次库调用线程安全，并不自动让业务中的全部步骤原子化。

例如“检查库存、扣减库存、记录订单”是复合操作。
单独把库存减一改成原子操作，不保证不会超卖，也不保证订单记录与库存保持一致。
需要按整体业务不变量选择锁、事务或经过验证的并发算法。

栈的分离解决执行现场的组织问题；共享数据的一致性是另一个需要明确设计的问题。
