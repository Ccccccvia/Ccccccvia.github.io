## 一个标识，通过 API 到达资源

句柄是 API 定义的不透明资源标识，具体表示可以是整数，也可以是指针形式的类型。
“不透明”表示调用者不应自行解释其位模式、推算资源位置或直接解引用。
句柄不是物理地址；即使普通指针可合法解引用，常见用户态指针也通常是虚拟地址。

```text
不透明句柄 h → 对应 API → 有效性 / 类型 / 权限检查 → 资源操作
```

这是一条概念路径，不保证所有 API 都使用同一张句柄表或完全相同的检查顺序。
句柄隐藏实现细节，但不能自动修复错误的所有权或并发使用方式。

## 用 Windows 文件 HANDLE 看生命周期

以打开一个已存在的普通文件为例，只请求读取权限，不设置“关闭时删除”选项。
下表是概念生命周期，不是可编译的文件 I/O 程序。

| 阶段 | API 与概念动作 | 程序必须确认什么 |
| --- | --- | --- |
| 取得 | `CreateFile` 打开现有文件，得到 `HANDLE` | 是否成功；失败时返回 `INVALID_HANDLE_VALUE` |
| 使用 | 把句柄交给 `ReadFile`，请求读取 128 字节 | 返回状态、实际读取字节数，以及该调用模式的要求 |
| 受控访问 | 系统按句柄定位打开的文件对象 | 句柄有效、类型适用、已授予所需权限 |
| 关闭 | 所有者用 `CloseHandle` 关闭此次打开的引用 | 不再有代码需要使用该引用；不能重复关闭 |
| 关闭之后 | 本地值不再代表可继续使用的旧引用 | 停止使用旧值，避免残留别名继续调用 |

请求 128 字节不等于必定读到 128 字节；例如到达文件末尾时可能更少。
具体 API 的失败标记要逐项查契约，不能把所有句柄失败都统一判断为零。
正常路径和失败路径都要管理已经成功取得、仍由自己拥有的引用。

## 权限跟着引用走

Windows 进程私有的内核句柄通常在所属进程的句柄表中解释。
只读文件句柄不因调用者知道其数值，就自动获得写权限。

| 操作设想 | 为什么不能只看句柄数值 |
| --- | --- |
| 把数值发给另一个进程 | 对方的句柄表不是本进程的表 |
| 跨进程共享访问 | 需要遵守复制或继承机制及其权限规则 |
| 多个引用指向同一资源 | 各引用的权限和生命周期仍需分别管理 |

合法的复制或继承可能让多个引用指向同一内核对象。
这不代表所有句柄家族都具有相同的进程作用域或复制机制。

## Close 关闭的到底是什么

`CloseHandle` 结束的是这一个拥有的内核句柄引用，不是“删除磁盘上的文件”。
其他引用可能继续存在，底层对象也不保证立即销毁。
文件删除需遵循专门的文件 API 和语义；显式设置“关闭时删除”标志等情况另有规则。

关闭某个线程的句柄，也不等于要求该线程停止运行。
不要仅因变量仍保存着非零值，就认定引用仍然有效。

系统可能把已关闭的句柄值复用于新的资源。
即使旧值后来又被某次调用接受，也不能证明它仍代表原来的对象。
清空一个本地变量可减少误用，但不会自动清除其他位置保存的副本。

## 不同 API 家族，清理方式不同

| 取得的资源或引用 | 匹配的清理方式示例 |
| --- | --- |
| 普通拥有的内核 `HANDLE` | 通常是 `CloseHandle`，仍须查具体 API |
| 自己拥有的窗口 `HWND` | 按窗口规则使用 `DestroyWindow` |
| `GetDC` / `BeginPaint` / `CreateCompatibleDC` 得到的上下文 | 分别匹配 `ReleaseDC` / `EndPaint` / `DeleteDC` |
| `LoadLibrary` 增加的模块引用 | 使用 `FreeLibrary`；`GetModuleHandle` 本身不增加引用 |

名称都像“句柄”，不等于能统一交给 `CloseHandle`。
借用的引用也不因此转移所有权；未经契约授权，不应替所有者释放它。

## 生命周期也是并发问题

若线程 A 正在用一个句柄，线程 B 不能不顾使用协议就把同一引用关闭。
应用应明确谁拥有引用、谁可以借用，以及何时所有使用者都已结束。
API 内部检查不是对“使用与关闭竞争”的通用解决方案。

记住三件事：通过匹配 API 使用，按已授予权限操作，在有效且受管理的生命周期内关闭。
